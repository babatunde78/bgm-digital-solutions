# BGM product studio

Turn the owner's product idea into a complete, usable buyer package and a truthful storefront presentation. Work in this repository. Reuse supplied answers and existing assets rather than asking the owner to repeat them.

## Intake and pricing

Before authoring a new product, ask the owner:
- What is the product about, who is it for, and what problem should it help them solve?
- What should the buyer receive: a guide, workbook, templates, software/toolkit, training material, or a combination? Ask about essential topics, requirements, and supplied source material when the brief does not settle them.
- What is the NGN price? What USD reference value should appear beside it? The owner supplies prices; never invent, estimate, or convert a selling/reference price without an explicit instruction.

Bundle missing questions into one concise request. If the description is already supplied, clarify only material gaps. Do not start substantive product authoring or catalogue pricing until the brief and required owner-supplied prices are known; source inspection and research can proceed meanwhile. If the owner wants one currency only, respect that choice.

Distinguish product subject from supported claims. A title about jobs, income, scholarships, or clients does not authorize promises of those outcomes. For an update, establish which existing edition, prices, and buyer entitlements remain in force.

## Prepare the product

Read [the repository workflow](references/repository-workflow.md) before packaging or editing the storefront. Inspect the existing material and its consumers before choosing formats or fields.

Briefly state the buyer outcome, planned deliverables, files affected, checks, and reversibility before writing. Choose the smallest coherent package that fulfills the brief; do not create filler chapters or arbitrary page counts.

Research current or specialist claims using primary sources. Keep useful source attribution in the buyer material. Do not copy third-party courses, books, templates, or images into the product without rights. Use fictional data for demonstrations.

Use available document, PDF, spreadsheet, presentation, and image-generation skills when producing their formats; read their instructions first. If a required capability is unavailable, report the specific missing deliverable instead of substituting an empty file or claiming completion.

## Author and test

Write for the buyer's actual task: concrete instructions, realistic worked examples, useful checklists or exercises, and clear limitations. Avoid inflated adjectives, stock motivational introductions, repetitive summaries, and unsupported statistics. Do not add comments or explanations about how the content was generated to customer-facing material.

For guides, include enough context to make instructions usable, then demonstrate the work and give the buyer a way to apply it. For templates and software, supply working files, realistic fictional examples, requirements, setup/use instructions, and meaningful validation. A mockup is not a substitute for the actual toolkit.

Render and inspect each document in its final format. Check layout, pagination, table widths, links, typography, and consistency between the editable source and exported copy. Open and test worksheets, formulas, examples, scripts, and companion files as applicable. Never claim a file opens or a workflow works without checking.

After each substantial deliverable, review it skeptically: Is it accurate? Does it teach or do what the description promises? Are instructions complete? Could an example mislead? Fix defects before proceeding. Add behavior tests for software changes; avoid tests that merely mirror written copy.

## Design the images last

Finish the product and substantive storefront work before generating final product mockups, unless the owner requests a different order.

Use the built-in image-generation skill for raster artwork. Inspect the current images under `assets/` and match the BGM visual family: matte paper, warm ivory background, forest green/ink/sage/ochre, disciplined type, natural light, grounded shadows, generous margins, and accurate titles. Vary the cover composition and colour to suit each product while preserving the shared brand.

Generate purpose-specific mockups, inspect spelling and composition, then optimize and save selected images into the repository. Do not use robots, glowing abstract shapes, stock dashboards, fake reviews, or fabricated software screenshots. Mark illustrative mockups as such; do not imply physical delivery. If showing an actual interface or sample page, capture/render the real product.

## Package and integrate

Create the agreed buyer documents, tested companion resources, a concise getting-started file, and a versioned ZIP if appropriate. Keep deliverables in ignored `.product-work/<slug>/<version>/` until an authorized private-storage upload. Never commit paid buyer files or publish them as static assets.

Prepare storefront copy using the actual finished package: audience, short description, contents, requirements, limitations, price and reference value, access instructions, support, and the current seven-day digital-product refund policy. Do not invent licence terms, update rights, compatibility, testimonials, or service delivery commitments.

Integrate using the repository's existing catalogue and delivery contract. New products remain unpublished until the owner-provided price, private files, and delivery mapping are validated. Do not expose a Buy button from static reference metadata.

A request to create a product does not by itself authorize publishing, uploading private material, changing payment configuration, pushing, or deploying. Reuse explicit authorization already given for that product/task; do not inherit unrelated release approval from a previous task.

## Completion

Review the final package against the brief, inspect the diff for unrelated edits, run relevant checks, and report exact deliverable paths, validation results, and any missing capability or release step. Keep the report concise. Distinguish prepared, privately uploaded, published, and deployed; only report the state actually verified.
